# 提交与合规清单

规则补充日期：2026-07-22。本文把参赛要求转换为可验收事项；未勾选项目不应进入最终提交。

## A. 报名与组队

- [ ] 所有队员均已在管理系统完成注册。
- [ ] 每名队员只使用一个账号且只参加本队。
- [ ] 队员总数不超过 5 人。
- [ ] 已指定队长。
- [ ] 队伍名称不超过 15 个字符，并确认系统按字符还是字节计数。
- [ ] 2026-07-24 前锁定队员名单；任何后续整队合并均不拆分且合并后不超过 5 人。
- [ ] 保存报名成功、队伍成员和队长页面的截图。

## B. 第三方组件合规

为每项代码、模型、数据、工具和外部服务维护一条记录：

```text
名称 | 用途 | 公开 URL | 固定版本/提交 | 许可证 | 获取方式
是否需要特殊授权 | 是否允许再分发 | 提交中的声明位置
```

- [ ] 所有组件均有公开发布页面，不使用私有仓库、内部数据或未发布工具。
- [ ] 所有许可证与比赛使用、结果复现和可能的获奖代码公开相容。
- [ ] 需要单独商业授权、机构授权或个人邀请的组件已移除。
- [ ] 对需要账号/API key 的公开服务已取得组委会书面口径，并提供可复现配置说明。
- [ ] 第三方库和开源算法在技术报告中明确注明。
- [ ] 没有把 API key、token、cookie、个人路径或私有 URL 写入代码、日志、轨迹和 Git 历史。

建议从第一天维护 `THIRD_PARTY_NOTICES.md`，不要等提交前追溯来源。

## C. GitHub 代码提交

- [ ] 官网提交的是可访问的 GitHub 仓库链接。
- [ ] 仓库包含完整实现代码，而不是只有 patch、notebook 输出或二进制文件。
- [ ] 允许修改和禁止修改的官方目录边界有清晰说明。
- [ ] 固定官方 baseline 提交、Python 版本和全部直接依赖版本。
- [ ] 提供从干净环境开始的安装、配置、运行、轨迹生成和评分命令。
- [ ] 说明 Git LFS 权重/资产的获取方法、哈希和落盘位置。
- [ ] 提供不含秘密信息的 `.env.example`，真实凭证只由环境变量注入。
- [ ] 默认配置可以运行，所有路径均为相对路径或可配置路径。
- [ ] 至少在一台与官方评测接近的干净 Linux 机器完成端到端复现。
- [ ] 每个报告结果都能追溯到配置、随机种子、模型 checkpoint 和原始轨迹。

## D. 轨迹与结果

- [ ] 提交五个场景要求的机器人位置、关节角和可移动物体轨迹。
- [ ] 轨迹格式由官方模板或未修改官方代码验证。
- [ ] 报告分数由未修改的官方评分程序复算。
- [ ] 保存成功与失败运行，不只保留最佳轨迹。
- [ ] 报告完成度、用时、安全性/碰撞以及重复实验统计。
- [ ] L1-L4 具有匹配的成功抓取事件；L5 三件物体分别可追踪。

## E. 技术报告

- [ ] 以 `README.md` 或 PDF 提供完整报告。
- [ ] 技术描述覆盖系统架构、SOP 处理、规划、导航、抓取、放置、恢复和实现细节。
- [ ] 单列第三方代码、模型、数据和工具声明。
- [ ] 单列“新颖性声明”，说明与相关工作的差异、实际推进和引用依据。
- [ ] 提供定量结果、定性案例和消融实验。
- [ ] 讨论性能优势、失败案例、适用边界和局限性。
- [ ] 可选视频与报告中的代码版本、场景和结果一致。

## F. 获奖公开准备

- [ ] 团队确认接受获奖后随名单公开全部实现代码的要求。
- [ ] 仓库中所有自研代码的作者和版权归属清晰。
- [ ] 所有第三方许可证允许仓库按预定方式公开。
- [ ] 公开仓库不包含秘密、个人信息、未获许可的素材或不可再分发权重。
- [ ] 发布标签锁定最终代码、报告、配置、环境说明和结果索引。

## 最终验收原则

评测人员应能在没有开发者私下协助、没有开发机隐式文件、没有未公开资产的情况下，按照仓库说明重现报告结果。若做不到，就还不满足“完全可复现”。
