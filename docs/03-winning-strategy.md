# 竞赛技术路线

目标是先把 60% Performance 做成稳定的工程事实，再用同一套机制支撑 40% Innovation。总原则：可靠性优先、严格兼容官方评分、所有改动在允许目录内、每个结论由多次轨迹复现。

## 系统方案

```text
DOCX 文本/图片
  -> VLM 结构化抽取
  -> schema + 证据 + 地图一致性验证
  -> 确定性任务图/行为树
  -> 安全导航 / 抓取 / 放置技能
  -> 状态验证与有限恢复
  -> 官方轨迹与未修改评分器
```

LLM/VLM 不直接输出底盘或关节动作。它只处理语义不确定性；物理执行使用可测试的技能和显式约束。

截至 2026-07-28，方案 B 已在官方固定种子下完成五关满分和零碰撞。当前实际主抓取策略已从“优先复用 BC”收敛为“对象族几何 OSC/约束 IK 主策略，学习策略作为证据驱动后备”。结果和边界见 [`09-current-route-and-optimization-plan.md`](09-current-route-and-optimization-plan.md) 与 [`2026-07-28-five-level-performance-baseline.md`](../experiments/2026-07-28-five-level-performance-baseline.md)。

## 分阶段里程碑

### M0：规则锁定与环境准备

- 7 月 24 日前确保每名队员完成注册，确定不超过 15 字符的队名、队长和最多 5 人的最终名单，并加入官方群。
- 向组委会提交 [`05-open-questions.md`](05-open-questions.md) 中的关键规则问题。
- 在 Linux + 24 GB GPU 环境补齐 Git LFS 权重，固定官方提交和依赖版本。
- 保存未修改官方 scorer 的哈希，建立轨迹离线复算入口。
- 建立第三方依赖清单，逐项记录公开来源、版本、许可证、模型/数据获取方式和是否需要特殊授权。

退出条件：官方 UI/无头环境能加载 L1，权重、地图、相机观测和轨迹记录都完整。

### M1：L1 可复现满分

- 先绕开语言规划的不确定性，用固定的结构化计划验证物理闭环。
- 检查导航、base approach pose、BC 观测方向、`sim.forward()`、lift verification 和放置。
- 每次运行保存事件、轨迹、碰撞、最终坐标和官方分数。

退出条件：未修改官方 `app.py` 连续多次得到 10/10，且 `grasp_end success=true`、零碰撞。

### M2：L2-L4 泛化

- 扩展对象映射和每关接近姿态。
- 对每个场景建立最小演示集；先复用 BC，再决定是否训练场景专用策略。
- 为导航加入 clearance 代价、载荷 footprint 和线段碰撞复核。

退出条件：L1-L4 在固定评测协议下稳定满分或明确定位唯一瓶颈。

### M3：L5 三对象闭环

- 在 workflow 中实现三对象显式循环，不依赖默认四步 LLM 计划。
- 每件物体独立记录 `pending/grasped/placed/verified` 状态。
- 单件失败只重试当前对象；已放置对象不可被后续路径碰撞或带走。

退出条件：三件物体都有匹配成功抓取事件、全部到达 `aux_output_1`、零碰撞、30/30。

当前状态：固定种子已达到退出条件；下一门槛是 20 种子稳定性和等待时间消融。

### M4：原创 SOP 解析器

- DOCX 文字、表格、关系与图片分开抽取。
- VLM 输出严格 schema；所有字段带文本或图片证据。
- 对 Erratum、任务图片、semantic map、对象集合做一致性检查。
- 生成自己的 Markdown 知识库，并保存输入哈希、模型、提示词和生成日志。

退出条件：五份 SOP 自动生成结果与人工参考功能等价，但内容来源可证明为自研流水线。

### M5：消融、压力测试和报告

- 对比 baseline、仅安全导航、仅 SOP 校验、完整系统。
- 每场景使用相同种子集合重复运行，报告成功率而不是最好一次。
- 报告碰撞率、抓取成功率、到达率、耗时、路径长度和重试次数。
- 把失败案例、恢复行为和限制写入创新报告，避免只展示成功视频。
- 在干净 Linux 环境按 README 从零复现，生成最终 GitHub 提交仓库、依赖锁定文件、轨迹、报告和可选视频。
- 执行 [`06-submission-compliance.md`](06-submission-compliance.md) 的发布审计，确保获奖后可以公开全部实现代码且不泄露密钥。

## 实验优先级

| 优先级 | 工作 | 原因 |
|---|---|---|
| P0 | 报名、规则确认、环境与 LFS | 截止日期和可运行性是硬门槛 |
| P0 | 依赖许可与公开性清单 | 私有/未授权组件会直接造成资格风险 |
| P0 | L1 未改 scorer 满分复现 | 验证整条物理与评分链 |
| P0 | L5 多对象 workflow | 官方 baseline 的最大结构缺口 |
| P1 | 零碰撞导航与 approach pose | 直接提升所有关卡、碰撞代价高 |
| P1 | 五场景抓取数据/策略 | 物理成功率的主要风险 |
| P1 | 可追溯 SOP 解析 | 同时满足规则和创新评分 |
| P2 | SmolVLA / OpenVLA-OFT 小规模试验 | 只有在基线稳定且数据到位后才值得 |
| P3 | GR00T、cuRobo 全量集成 | 时间和接口风险过高 |

## 统一实验协议

- 固定官方提交、方案提交、依赖锁文件、硬件和 MuJoCo 渲染后端。
- 每个场景至少使用多个固定种子重复运行；开发期先 5 次，正式报告建议 20 次以上。
- 主要指标：官方分数、整任务成功率、碰撞率。
- 次要指标：抓取成功率、放置到达率、路径长度、耗时、重试数、API 调用数。
- 不修改 scorer，不手工改轨迹，不只保留成功 run。
- 每次失败只改变一个假设，并在 [`experiments/experiment-log.csv`](../experiments/experiment-log.csv) 记录。
- 每个第三方组件都固定公开版本和许可证；模型、数据与权重提供公开下载或合规获取说明。

## 决策门槛

- 若固定 pose + 官方 BC 已能稳定抓取，不立即训练 VLA。
- 若失败集中在图像域偏移，先修复观测预处理和小规模 BC 微调。
- 若失败集中在多峰动作，才评估 Diffusion Policy/SmolVLA。
- 若导航碰撞存在，先降低风险与增加 clearance，不以提速掩盖失败。
- 只有完整混合系统稳定后，才把时间作为同分优化目标。
